Performance · 01 约 7 分钟

前端性能优化实战

从 FCP 到 INP，记录真实项目中的性能瓶颈排查与优化过程。

为什么性能优化总是"做了但没变化"？

我遇到过很多次这种情况：团队花了两个迭代做性能优化，Lighthouse 分数从 62 涨到 71，但用户反馈"感觉没快多少"。原因几乎都一样：优化的指标和用户感知的指标对不上。

性能优化的起点不是跑分，是弄清楚用户在哪个环节感到"慢"。FCP（首次内容绘制）、LCP（最大内容绘制）、INP（交互到下一帧）这三个指标，对应的是三种完全不同的慢。

FCP 慢：页面白屏太久

FCP 慢通常有两个主因：渲染阻塞资源太多，或者服务端响应慢。前者我们能直接控制，后者需要和后端配合。

前端侧最有效的几个手段：

  • 内联关键 CSS。首屏用到的样式直接写在 <style> 里，消除一次网络往返。我们在一个中台项目里做完这个，FCP 从 2.1s 降到 1.3s。
  • 预加载关键字体。<link rel="preload"> 配合 font-display: swap，避免字体加载期间文字不可见（FOIT）。
  • 减少初始 JS 体积。路由级懒加载是标配，但更容易被忽略的是：组件库按需引入、第三方库的 tree-shaking 是否真正生效。

LCP 慢：主内容出现太晚

LCP 元素通常是页面最大的图片或文字块。最常见的问题是：Hero 图片没有设置 fetchpriority="high"，导致它和其他资源排队加载。

另一个容易踩的坑是 SSR/SSG 项目里，LCP 元素是通过 JS 动态插入的。浏览器扫描 HTML 时找不到它，就不会提前调度加载。这种情况要把 LCP 内容放进初始 HTML，而不是依赖客户端渲染。

我在数据可视化项目里遇到过 LCP 是一张 1.2MB 的背景图——改成 WebP + 显式尺寸 + fetchpriority="high"，LCP 从 4.8s 降到 1.9s，不需要任何架构改动。

INP 慢：点了没反应

INP 是 2024 年 Core Web Vitals 新增的指标，衡量的是从用户交互到浏览器响应的延迟。它比 FID 更全面，因为它覆盖整个会话里所有交互的 P98 延迟。

INP 差的根源通常是主线程被长任务阻塞。排查工具：Chrome DevTools 的 Performance 面板，看 Main 线程里有没有超过 50ms 的 Task。

  • 把长列表渲染拆成分批任务。用 scheduler.postTask 或 setTimeout(0) 把大量 DOM 操作切片，让浏览器有机会响应用户输入。
  • 事件处理函数里别做重计算。把耗时的逻辑移到 Web Worker，或者用 useDeferredValue（React）/ v-memo（Vue）减少不必要的重渲染。
  • 减少全局状态更新的扩散范围。一次 store 更新触发几十个组件重渲染，每个组件都触发一次 diff，累积起来很可观。

工具链选择

日常用 Chrome DevTools Performance 面板做初步定位；用 web-vitals 库在真实用户环境采集线上数据（RUM）；Lighthouse 只作为参考，不作为唯一依据。

线上数据比 Lab 数据更重要——用户的设备、网络、使用场景都比你的开发机复杂得多。

最后一句话

性能优化没有通用公式，但有通用思路：先测量、找到真正的瓶颈、对症下药、再测量验证。跳过测量直接优化，大概率是在做无用功。

Tooling · 02 约 5 分钟

AI 如何改变前端工作流

Claude、Cursor 深度上手体验，以及它们真正改变了哪些开发环节。

从"辅助输入"到"协作思考"

最开始用 AI 工具，我把它当成一个更快的代码补全——帮我写样板代码、生成类型定义、补全重复逻辑。这个阶段提效是有的，但还谈不上改变工作方式。

真正让我觉得"不一样了"，是当我开始把它当成一个可以对话的技术协作者：描述问题、讨论方案、让它给出不同实现路径的权衡分析。这个时候，它的价值不再是"打字快"，而是压缩了思考和决策的成本。

Cursor：编辑器级别的上下文感知

Cursor 最大的优势是它能读懂整个项目。当我改一个组件，它知道这个组件在哪里被引用、Props 是什么、相关的类型文件在哪——不需要我反复解释上下文。

几个实际用到的场景：

  • 重构辅助。把一段老代码粘进去，说明目标（比如"拆成 composable，分离副作用"），它给出的方案通常可以直接用或者稍作调整。
  • 多文件联动修改。改接口字段时，它能定位到所有受影响的文件并批量更新，这个以前要靠全局搜索 + 手动替换。
  • 写测试。我对单测一直有惰性，Cursor 能根据函数签名和实现自动生成测试用例，覆盖率检查后再补边界 case，阻力小了很多。

Claude：更适合"想清楚再动手"的场景

Claude 我主要用在两类场景：一是设计阶段，二是排查复杂问题。

设计阶段：把需求和现有系统的约束描述清楚，让 Claude 分析几种方案的利弊。它不会急着给代码，会先把问题拆开来讲——这一点在做架构决策时很有价值，因为你需要的不是"最快的答案"，而是"想清楚再动"。

排查问题：遇到诡异的 bug，把报错、相关代码、复现条件一起丢进去，Claude 的推理过程比直接给答案更有用——它会把可能的原因列出来，解释为什么排除某些可能性。这个过程本身就是在帮你建立排查思路。

没有改变的部分

AI 工具让我写代码更快，但没有替代我对系统的判断。什么时候该拆组件、这个接口设计合不合理、这个性能问题值不值得现在修——这些判断仍然需要我来做，AI 给的建议需要我来筛选和验证。

另一个没变的：代码 Review。AI 生成的代码有时候能用，但不一定符合团队规范、不一定考虑了边界情况、不一定和项目里其他模块的风格一致。Review 的门槛反而提高了，因为你要判断的不只是"能不能跑"，还有"是不是真的对"。

我的结论

AI 工具真正改变的是信息密度：同样的时间里，我能处理更多上下文、探索更多方案、验证更多假设。但工程判断力、对系统的整体理解、对质量的把控——这些还是人的事，而且因为 AI 提速了执行，这部分的比重反而更高了。

Engineering · 03 约 6 分钟

组件设计的底层逻辑

从业务抽象到接口设计，聊聊我理解的好组件应该长什么样。

什么是"好组件"？

做了 5 年前端，我经历过两种极端的组件：一种是完全按设计稿切出来的 UI 积木，没有任何业务感知；另一种是把数据请求、状态管理、权限判断全塞进 template 里的"巨石组件"。两种都很难维护。

好组件的核心标准只有一条：它的边界是清晰的。调用方不需要知道它内部怎么实现，组件自身也不需要知道谁在用它。这个"不知道"，才是组件设计真正要追求的东西。

单一职责不是"只做一件事"

大多数人理解的单一职责是：一个组件只渲染一块 UI。但这是字面意思，不是底层逻辑。

真正的单一职责是：组件只有一个变化的理由。如果一个组件既要跟着"设计规范改"变，又要跟着"业务逻辑变"，又要跟着"接口字段变"，那它就违反了单一职责——不是因为它"做了三件事"，而是因为它有三个变化源头，三个方向都可能让它崩。

实践中我的做法是：把数据转换逻辑抽成 composable（Vue）或 hook（React），把展示结构留在组件里，把业务条件判断提升到父级。三层分开，各自独立演化。

Props 接口是组件的"契约"

Props 设计是组件质量最直观的衡量标准。一个设计得好的 props，甚至不需要看实现就能猜到组件的边界。

几个我反复验证过的原则：

  • 不要透传原始数据结构。把接口返回的 UserDTO 直接扔进 props，组件就和接口耦合了。宁可在父级做一层 map，传进来的是组件真正关心的字段。
  • 布尔 props 命名要表达意图，不要表达状态。isLoading 比 loading 好，isDisabled 比 disabled 好——前者是状态描述，后者在不同语境下容易产生歧义。
  • 回调命名用 on + 动词过去时。onSubmit、onSelect，调用方一看就知道这是事件响应，而不是主动触发的方法。
  • 能派生的值不要单独作为 prop 传入。如果 isSelected 可以从 value === selectedId 里算出来，就不要同时传两个。状态越少，一致性问题越少。

组合优于继承，在组件层面同样成立

在业务中后台项目里，我遇到最多的问题是：一个基础组件被"魔改"了七八个变体，每个变体又被拿去当基础组件再魔改。这是继承思维，不是组合思维。

组合的做法是：把最小可复用单元做稳，然后用 slot / children / renderProps 的方式把它"插"进不同的容器。容器负责布局和上下文，原子组件负责交互和视觉，两者互不侵入。

我在公司组件库里推行过一个规范：基础组件不允许有业务 if 判断。一旦某个基础组件开始出现 if (type === 'admin')，就说明它该被拆了。

受控与非受控：别让调用方猜

表单类组件最容易踩的坑是：组件内部维护了一份状态，同时又接受外部的 value prop，结果两份状态打架。

选择受控还是非受控，本质上是在选择"谁来管状态"。基础 UI 组件（如 Input、Select）提供非受控模式作为默认，方便快速使用；业务组件、表单组合组件一般走受控，保证父级能完整掌控提交时机和联动逻辑。关键是——明确告诉调用方这个组件是哪种模式，不要让人猜。

最后

组件设计没有银弹，但有方向：让变化的东西变得容易变，让稳定的东西真正稳定。边界清晰的组件，测试好写、重构安全、接手的人也不会骂你。

这些判断都来自真实的业务教训，不是理论推演——哪个坑踩过，就会记得。
